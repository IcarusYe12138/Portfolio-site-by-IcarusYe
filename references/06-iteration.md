# 06 · 迭代改进节奏与三层文档体系

> 反面模式：一边聊一边改、想到哪改到哪——改动互相覆盖、决策无记录、返工频繁。
> 正面模式：**书面迭代**——先文档后代码，一轮一主题，一轮一次执行完。
> 完整体系分**三层**：改版总规（蓝图层）→ 轮次决策日志（过程层）→ 站根活档（沉淀层）。

## 〇、三层文档体系总览

| 层 | 载体 | 生命周期 | 回答的问题 |
|---|---|---|---|
| ① 改版总规 | 一次性的《XX 改版计划》文档 | 大版本启动时写一次 | 「要做成什么样、分几步」 |
| ② 轮次决策日志 | `改进建议-第N轮.md` × N | 每轮一份，写完即冻结（只补状态） | 「这一轮改了什么、为什么」 |
| ③ 站根活档 | 站根 `ITERATION.md` | 随代码长期维护 | 「这站现在是什么架构、有什么约束、踩过什么坑」 |

三层的分工：总规**向前看**（还没做的事），日志**向当下看**（正在做的事），活档**向后看**（已经沉淀的事）。新会话/新协作者按 ③ → ② → ① 逆序读，10 分钟接手。

## 一、① 改版总规（大版本蓝图）

动大版本（全新建站 / 整体改版）前写，结构模板：

```markdown
# XX 改版计划 · <风格关键词> × <架构关键词>
> 日期 / 目标目录 / 设计唯一规范（书面 Style Spec，见 01 文档）
> 用户决策记录（几轮澄清的结论，逐条列）

## Summary（概要）——一段话说清做什么
## Current State Analysis（现状分析）
   - 已探索完毕的事实（设计指南、旧站内容清单、素材盘点、部署限制……逐条列）
   - 旧设计作废项（明确写「作废」，防止旧方案回魂）
## Proposed Changes（改动方案）
   - 目录结构（完整树）
   - 设计系统 token 表
   - 逐页方案（每页一节：区块顺序、内容来源、交互）
   - 交互动画系统（编号清单 + 时长纪律）
   - 分区链接映射（海外/内地对照表，见 03 文档）
## 执行顺序（Todo 编号列表，从建目录到上线）
```

**纪律**：总规里「已探索事实」必须先盘点再开写——很多「方案反复」其实是前期没查清素材/限制。

## 二、② 轮次决策日志（每轮一份）

每轮启动时建一份「第 N 轮迭代改进建议」文档，每条改进项按固定格式记录：

```markdown
### #编号 — 一句话标题
**用户原话**：「……」（原样保留，这是需求的唯一事实源）
**根因**：为什么会这样（先诊断再开方）
**方案**：具体改哪些文件、怎么改（落实到文件路径级别）
**状态**：✅ 已完成 / ⏸ 暂缓 / ❌ 否决
```

**纪律**：
1. **先文档后代码**：所有决策锁定在文档里，才开始执行；
2. **一轮一主题**：一轮聚焦一类事（地基轮 / 组件轮 / 视觉轮 / 性能轮 / 收尾轮），不混做；
3. **一轮一次执行**：同一文件的多个修改集中在一次编辑会话完成（防并行编辑竞态，见 07 坑 #2）；
4. **否决也要记录**：被用户否掉的方案（如某些动效）写明「已否决」，避免后续 agent 再提；
5. **文档即 changelog**：迭代完成后把每轮一行（轮号 + 日期 + 主题 + 条数）写进站点的「制作说明」页（colophon），公开透明。

## 三、③ 站根活档（ITERATION.md）

放在站根、随代码一同维护的备案文件。写完轮次日志后，把**结论**（非过程）沉淀进来。固定章节：

```markdown
# 站点名 — 迭代改进留档（备案）
> 线上地址 / 仓库位置 / 最后更新

## 一、项目概览        —— 定位、技术栈、语言（3~5 行）
## 二、技术架构        —— 层×方案×说明 的表（页面/样式/脚本/字体/媒体/安全）
## 三、页面清单        —— 每页一行：路径 + 说明
## 四、组件实现        —— 每组件一小节：机制要点 + 关键参数（如磁贴 density/pow/cell）
## 五、迭代历史（按主题） —— 不逐轮流水账，按主题归纳（视觉/导航/语言/作品区/响应式/部署）
## 六、硬性约束        —— 单文件上限、缓存纪律、文案纪律等「不可违反」清单
## 七、经验教训        —— 踩坑速记（详细版在轮次日志，这里留索引级）
```

**活档 vs 日志**：日志记过程与用户原话，活档只记**当前有效的结论**；被推翻的旧做法在活档里直接删（不翻旧账），在日志里留痕即可。

## 四、推荐轮次节奏（从 0 到上线的骨架）

| 轮 | 主题 | 干什么 |
|---|---|---|
| 0 | 方案探索 | 可以先试框架原型，**允许废弃**——废弃决策记录在案（「React + Vite 原型，废弃」） |
| 1 | 静态基线 | 手写 HTML/CSS/JS 骨架：页面清单、token、断点、字体 |
| 2 | 导航与语言 | 顶栏、语言切换架构、三语机制定型（结构决策越早越好） |
| 3 | 字体与网格 | 字族体系、响应网格、作品索引 |
| 4 | 组件 | 卡片、滚动条拖拽、案例媒体、合并冗余区块 |
| 5 | 视觉母题 | 装饰场（磁贴/点阵）、导航交互、徽标 |
| 6 | 一致性 | 404 三语化、页脚统一、hover 细节 |
| 7 | 减法 | 退役过度设计（花哨动效、多余指示器）——**做减法是必经轮** |
| 8 | 修复与提示 | 竞态修复、可滑动提示等微交互 |
| 9 | 性能与收尾 | 字体分片、og:image、robots/sitemap、语言检测 |

要点：
- **第 7 轮式的「减法轮」几乎必然出现**——前几轮加的动效/装饰，用户看完整体后总会要求删一部分；预留这一轮，心态不崩；
- 性能大项（字体分片、分享图）放后轮——先保证功能与视觉正确，再优化载荷；
- 每轮结束做一次「版本号 bump + 线上验证」，小步上线。

## 五、需求沟通模式

- 用户反馈「看起来特别花 / 哪里不对」时：**先找根因参数**（如磁贴密度曲线、透明度档数、翻转比例），给出参数级修改方案，而不是整个推倒；
- 拿不准的视觉决策：给 2~3 个参数方案让用户选，而不是开放式问「你想要什么」；
- 用户明确说「删掉」时：**彻底删**（HTML + CSS + JS + 字典 key 四处同步），不留「以后可能还要」的残留——残留代码是最常见的二次返工源。

## 六、大改后的自查

- [ ] `wc -l` 抽查核心 HTML 行数是否在正常区间（防快照污染，见 07 坑 #3）
- [ ] 控制台零报错、三语切换正常
- [ ] 改过 CSS/JS → 全站 `?v=` 已 bump
- [ ] 线上（非本地）抽测一个页面
- [ ] 轮次日志全部条目标状态；结论性变更已同步进站根活档
